1️⃣ الفكرة الكبرى: تطبيق الويب مثل مطعم

تطبيق الويب = متصفح يطلب، خادم يقرر، تطبيق ينفذ المنطق، قاعدة بيانات تحفظ، وHTTP ينقل الكلام بينهم. الأمن يعني ألا نسمح لطلب غير موثوق أن يتحول إلى أمر خطير.
Browser / Client
المستخدم يرى الواجهة: HTML/CSS/JavaScript، ويرسل GET/POST.
Web App Security = حماية الرحلة من الطلب إلى البيانات
Web Server / App
يعالج الطلب، ينفذ منطق الأعمال، ويتواصل مع DB/API.
Database
تخزن المستخدمين، الجلسات، الطلبات، التعليقات.
HTTP/HTTPS
لغة الطلب/الرد. HTTPS يضيف تشفيراً وحماية أثناء النقل.
Security
مصادقة، تفويض، جلسات، تحقق إدخال، معالجة أخطاء، تحديثات.

تشبيه المطعم

العميل = Browser

يطلب وجبة عبر قائمة. لا يدخل المطبخ.

النادل = Web Server

يستقبل الطلب ويرسله للمطبخ.

المطبخ = Application Layer

ينفذ منطق العمل: هل الطلب صحيح؟ هل المستخدم مصرح؟

المخزن = Database

يحفظ البيانات. الوصول إليه يجب أن يمر عبر قواعد.

الفاتورة/الهوية = Session/Cookie

تُستخدم لمعرفة من أنت بين الطلبات.

الأمن = Validation/AuthZ

لا تقبل طلباً غريباً ولا تسلم المخزن لأي شخص.

قاعدة ذهبية للامتحان

معظم الثغرات في الملفات تعود إلى جذر واحد: خلط البيانات بالكود أو الثقة في إدخال المستخدم. SQLi يخلط إدخال المستخدم مع SQL، وXSS يخلط إدخال المستخدم مع JavaScript/HTML، وCommand Injection يخلط الإدخال مع أوامر النظام.

3️⃣ ملف 1: Introduction — لماذا ندرس أمن تطبيقات الويب؟

الملف الأول يقول إن كثيراً من الأعمال الحساسة أصبحت عبر الويب: بنوك، تسوق، خدمات، APIs. لذلك أي ضعف في تطبيق الويب قد يتحول مباشرة إلى سرقة حسابات، تسريب معلومات، خسارة ثقة، أو ضرر سمعة.

الأهداف العامة للمقرر

فهم معمارية تطبيقات الويب الأساسية
فهم بروتوكولات HTTP/HTTPS
التعرف على الهجمات الشائعة مثل SQL Injection وXSS
فهم الاختبارات الأمنية للتطبيقات
تعلم كيف تقلل الاختبارات المخاطر
ربط الثغرة بتأثيرها التجاري والتقني

كيف يقلل الاختبار الأمني الخطر؟

يربط الثغرة بالنتيجة: وصول لمحتوى مقيد، اختراق حسابات، كود ضار، خسارة مبيعات، فقدان ثقة، ضرر سمعة.

سؤال متوقع

فرّق بين SAST وDAST: SAST ينظر إلى الكود قبل/دون تشغيل التطبيق، DAST يختبر التطبيق وهو يعمل. Pen Test يدوي وأكثر مناسبة للتطبيقات الحرجة والمنطق المعقد.

4️⃣ ملف 2: Web Application Architecture — خريطة المدينة

المعمارية هي معرفة أين يوجد كل مكوّن وكيف يتحدث مع الآخر. بدون هذه الخريطة لن تفهم أين تقع الثغرة.

مكونات معمارية تطبيق الويب

User Agent

غالباً المتصفح. أداة المستخدم للتفاعل مع الخادم.

DNS

دفتر عناوين الإنترنت: يحول اسم الموقع إلى عنوان IP.

Load Balancer

يوزع الطلبات على أكثر من خادم لتحقيق التوسع الأفقي.

Virtual Machine

محاكاة/افتراضية لنظام حاسوب لتشغيل تطبيقات وخدمات.

Web Server

يستقبل طلب المستخدم ويرسل استجابة: صفحة، ملف، أو نتيجة معالجة.

Database

تنظيم وإضافة وبحث وتحديث وحذف وحساب البيانات.

Caching Service

تخزين مؤقت لتحسين السرعة وتقليل الضغط.

CDN

شبكة خوادم موزعة جغرافياً لتقديم المحتوى قريباً من المستخدم.

External Storage

تخزين صور، فيديو، مستندات، وملفات كبيرة، غالباً سحابياً.

Web Services

منصة تواصل بين تطبيقات بلغات مختلفة.

Data Warehouse

مستودع مركزي للتقارير والتحليل وذكاء الأعمال.

1

←
2

قوة 3-tier أنها تفصل المسؤوليات. يمكنك تحديث الواجهة دون تغيير قاعدة البيانات، أو تغيير DBMS دون تغيير كل الواجهة. أمنياً: لا ينبغي أن يتحدث العميل مباشرة مع قاعدة البيانات؛ يمر عبر طبقة تطبيق تتحقق من الصلاحيات والمنطق.

كيف يعمل Web Server؟

العميل يحدد مستنداً أو مورداً بعنوان URL.
الخادم يستقبل الطلب عبر HTTP/HTTPS.
إذا كان الملف ثابتاً يرسله، وإذا كان سكربتاً ينفذه على الخادم.
الخادم يرسل الناتج فقط للعميل.

فكرة أمنية مهمة من الشرائح

العميل لا يرى كود الخادم Server-side code. إذا رأى المستخدم أسراراً أو مسارات داخلية أو رسائل خطأ مفصلة، فهناك مشكلة تصميم/إعداد.

5️⃣ API — كيف تتكلم التطبيقات مع بعضها؟

API هي مجموعة قواعد ومعايير تسمح للبرامج بالتفاعل وتبادل البيانات. هي وسيط بين تطبيقين، وليست بالضرورة واجهة يراها المستخدم.

6️⃣ ملف 3: HTTP — لغة الكلام بين المتصفح والخادم

HTTP هو بروتوكول طلب/استجابة. المتصفح يطلب، والخادم يرد. إذا فهمت الرسالة، ستفهم أين تدخل الثغرات.

7️⃣ Cookies, Web Cache, HTTPS — الحالة، السرعة، والحماية أثناء النقل

لماذا نحتاج Cookies؟

HTTP بطبيعته Stateless: كل طلب مستقل. الخادم لا يتذكر تلقائياً من أنت بين طلب وآخر. لذلك تستخدم المواقع Cookies لتعريف المستخدم أو الجلسة.

1
Loginالمستخدم يسجل الدخول.
←
2
Session IDالخادم ينشئ معرف جلسة.
←
3
Cookieالمتصفح يخزنها ويرسلها مع الطلبات.
←
4
Stateالخادم يعرف أن هذا الطلب من نفس المستخدم.

ماذا يمكن أن تقدم Cookies؟

Authorization / Authentication state
Shopping carts
Recommendations
User session tracking
Preferences
مخاطر خصوصية إذا أسيء استخدامها

Session Hijacking

إذا سُرق Session Cookie، قد يستطيع المهاجم تقليد جلسة المستخدم. لذلك HTTPS، وخصائص مثل HttpOnly/Secure/SameSite، وتسجيل الخروج، وإدارة الجلسات مهمة جداً.

Web Cache / Proxy Server

الكاش يعمل كعميل وخادم: يطلب المحتوى من الخادم الأصلي، ثم يخزنه ليقدمه بسرعة لطلبات لاحقة. الفائدة: تقليل زمن الاستجابة والضغط على الخادم.

8️⃣ ملف 4+5: Web Security — من أين يأتي الخطر؟

Web Application Overview

مثال Command Injection من الشرائح — الفهم الآمن

الشرائح تعرض صفحة “Ping for FREE” تأخذ IP من المستخدم ثم تستخدمه في أمر نظام. الخطأ: إدخال المستخدم يُدمج في أمر Shell دون تحقق كافٍ. لو أضاف المستخدم رموزاً خاصة، قد لا يبقى الإدخال مجرد IP، بل يصبح جزءاً من أمر جديد.

الكود الخطر من حيث الفكرة

أخذ ip من الطلب ثم تمريره مباشرة إلى shell_exec. المشكلة ليست ping نفسه؛ المشكلة هي الثقة بالإدخال.

الإصلاح في الشرائح

التحقق أن الإدخال IP صالح باستخدام filter_var(..., FILTER_VALIDATE_IP) واستخدام escapeshellarg عند الحاجة. والأفضل عموماً تقليل أو تجنب استدعاء Shell عندما يمكن استخدام مكتبة آمنة.

عبارة امتحانية جاهزة

Command Injection يحدث عندما ينتقل إدخال المستخدم غير الموثوق إلى مفسر أوامر النظام. الدفاع: Validate allowlist، استخدام APIs آمنة بدلاً من Shell، escaping مناسب، وأقل صلاحيات.

مبدأ “لا تثق بالعميل”

أي تحقق يحدث فقط في JavaScript يمكن تجاوزه. العميل يستطيع تعديل الطلب، حذف JavaScript، تغيير parameters، أو استخدام أداة إرسال طلبات. لذلك التحقق الحقيقي يجب أن يكون على الخادم.

Checklist مصغر قبل نشر تطبيق

  • هل كل الإدخالات لها validation واضح؟
  • هل كل مخرجات المستخدم encoded حسب السياق؟
  • هل SQL يستخدم prepared statements؟
  • هل رسائل الخطأ لا تكشف تفاصيل داخلية؟
  • هل جلسات المستخدم محمية بـ HTTPS وخصائص Cookies؟
  • هل التفويض يُفحص على الخادم لكل مورد؟
  • هل واجهات Admin محمية وغير مكشوفة؟
  • هل المكونات والخوادم محدثة؟
  • هل يوجد SAST/DAST/Pen Test حسب خطورة التطبيق؟
  • هل منطق العمل مختبر ضد الالتفاف؟

اشرح SQL Injection وطرق الحماية

SQL Injection يحدث عندما يستخدم التطبيق إدخالاً غير موثوق لبناء استعلام SQL، فيستطيع الإدخال تغيير معنى الاستعلام. تأثيره قد يكون قراءة أو تعديل بيانات أو تجاوز صلاحيات. الحماية تكون باستخدام parameterized queries، التحقق من الإدخال، أقل صلاحيات لقاعدة البيانات، وعدم إظهار أخطاء تفصيلية.

فرّق بين Reflected وStored XSS

Reflected XSS يأتي غالباً من رابط يحتوي إدخالاً ضاراً يعكسه الخادم في الرد، ويحتاج الضحية للنقر. Stored XSS يُخزن في الخادم مثل تعليق أو منشور ويصيب كل من يزور الصفحة، لذلك غالباً أخطر. الدفاع: ترميز الإخراج حسب السياق، sanitization موثوق، CSP، وحماية cookies.

اشرح 3-tier Architecture

تقسم تطبيق الويب إلى Presentation/Client layer للواجهة، Business/Application layer لمنطق الأعمال، وData Access layer للتعامل مع البيانات. فائدتها الفصل بين المسؤوليات وسهولة التحديث، وأمنياً تمنع العميل من التعامل المباشر مع قاعدة البيانات.

🃏 بطاقات مراجعة قلّابة اضغط البطاقة لتظهر الإجابة

ما الفكرة الكبرى لأمن تطبيقات الويب؟
حماية رحلة الطلب من المتصفح إلى الخادم والتطبيق وقاعدة البيانات، خصوصاً من إدخال غير موثوق.
الفرق بين SAST وDAST؟
SAST يفحص الكود دون تشغيل. DAST يفحص التطبيق وهو يعمل من الخارج.
متى يكون Penetration Test مناسباً؟
للتطبيقات الحرجة أو التي تخضع لتغييرات كبيرة، لأنه يدوي ويغطي منطق الأعمال وسيناريوهات متقدمة.
ما طبقات 3-tier Architecture؟
Presentation/Client، Business/Application، Data Access.
GET وPOST: الفرق الأساسي؟
GET يرسل البيانات في URL غالباً للقراءة. POST يرسلها في body للنماذج والإرسال.
لماذا نحتاج Cookies؟
لأن HTTP stateless؛ الكوكيز تساعد الخادم على تذكر الجلسة/المستخدم بين الطلبات.
HTTP vs HTTPS؟
HTTP غير مشفر عادة على 80. HTTPS مشفر عبر TLS ويستخدم غالباً 443، لكنه لا يصلح عيوب التطبيق وحده.
تعريف Injection؟
إرسال بيانات غير موثوقة إلى Interpreter فيتعامل معها كتعليمات.
أفضل دفاع ضد SQL Injection؟
Parameterized Queries / Prepared Statements مع validation وأقل صلاحيات.
Reflected vs Stored XSS؟
Reflected عبر رابط ينعكس في الرد. Stored يُخزن في الخادم ويصيب الزوار.
لماذا Sanitization ليست سهلة؟
لأن السياق مهم، والمهاجم قد يستخدم encoding/Unicode/طرق التفاف. لا يكفي حذف كلمة script.
Second-order SQLi؟
إدخال ضار يُخزن أولاً ثم يُستخدم لاحقاً في استعلام آخر فيسبب الحقن.

🧪 اختبار فهم تفاعلي

1) اختبار يفحص الكود المصدري دون تشغيل التطبيق غالباً يسمى:
SAST = Static Application Security Test.
2) اختبار يفحص التطبيق وهو يعمل من الخارج يسمى:
DAST = Dynamic Application Security Test.
3) طبقات 3-tier Architecture هي:
هذه هي الطبقات الثلاث في الشرائح.
4) في REST API، الطريقة المستخدمة غالباً لاسترداد البيانات هي:
GET لاسترداد معلومات عن مورد.
5) HTTP بطبيعته:
لذلك نحتاج cookies/sessions.
6) المنفذ الافتراضي لـ HTTPS هو:
HTTP غالباً 80 وHTTPS غالباً 443.
7) عندما يدخل إدخال المستخدم إلى SQL ويغير معنى الاستعلام فهذا:
SQLi = حقن داخل استعلام قاعدة البيانات.
8) أفضل دفاع أساسي ضد SQL Injection هو:
Prepared statements تفصل الكود عن البيانات.
9) XSS المخزن Stored XSS يعني أن السكربت:
Stored XSS أخطر لأنه يصيب من يزور الصفحة.
10) حذف كلمة <script> فقط يعتبر دفاعاً غير كافٍ لأن:
Sanitizing is not easy؛ نحتاج دفاعاً حسب السياق.
11) إذا كان المستخدم A يستطيع الوصول لبيانات المستخدم B بتغيير id في الرابط، فهذا غالباً:
المشكلة تفويض أفقي/تحكم وصول.
12) Second-order SQL Injection يحدث عندما:
الهجوم يظهر في مرحلة/وظيفة لاحقة.

🎯 الخلاصة النهائية

إذا أردت جملة واحدة تحفظ المادة: تطبيق الويب يستقبل طلبات HTTP من عالم غير موثوق، والأمن هو منع هذه الطلبات من التحول إلى أوامر خطيرة أو وصول غير مصرح. كل شيء في الملفات يدور حول هذا: معمارية، API، HTTP، Cookies، HTTPS، Injection، SQLi، XSS، Sanitization، واختبارات الأمان.
